# Radio ranging as an opponent-identity signal for 2–4 player Quick Duel (BIO-37)

Status: Research complete — 2026-09-27. Read-only brief for [BIO-37](https://linear.app/biossphere/issue/BIO-37). Builds on — does not repeat — [zero-step-architecture-synthesis.md](zero-step-architecture-synthesis.md) and the seven BIO-36 briefs, and on §Option C of [shared-arena-frame-options.md](shared-arena-frame-options.md), which evaluated Nearby Interaction (NI) as a *shared-frame* source. That question is closed: the shared-frame / Saved Arena concept (ADR 0010/0011/0012, `SharedArena`/`DuelFrame`, `NearbyRendezvousCoordinator`) is being removed. This brief asks a different question — can a radio tell a sighting *which* opponent it is looking at — and evaluates NI, Bluetooth RSSI, and camera-ray fusion only for that.
Method: repository facts verified on `main` at `3d89b7f`; Apple primary documentation and WWDC transcripts re-read on 2026-09-27; practitioner and academic sources are marked **[practitioner]** / **[academic]**; inference is marked **(inference)**; anything Apple does not publish is stated as an absence. No physical device was used in this sprint; nothing here is physical-device evidence.

## 1. The question

Quick Duel (ADR 0013) is the only play mode. Each phone runs its own AR frame; the match Durable Object (`CombatRoom`) is combat authority; start is never gated by setup. A body sighting from the camera cannot tell *which* opponent is in view, so the mode is 2-player only. The owner wants 2–4 players with zero setup. Can Ultra Wideband (UWB) ranging via Apple Nearby Interaction, or Bluetooth signal strength, supply the missing identity — in the shooter's *own* frame, with no alignment step — and what happens on phones without UWB?

## 2. Where identity is decided today (repository facts, verified)

- **Client picks the target.** `RealtimeAssociationPolicy.associateSighting` ([RealtimeBodyAssociation.swift](../../ios/VictoriaKillZone/VictoriaKillZone/Features/Realtime/RealtimeBodyAssociation.swift)) requires a skeleton captured ≤ 0.1 s ago, observation confidence ≥ 0.8, and **exactly one connected remote player**; it returns that player with `marginMeters = .infinity`. With two or more opponents it returns `nil` and no sighting is attached to the fire command. The older `associate(...)` path (hand-to-phone ≤ 0.45 m, nearest-candidate margin ≥ 0.35 m) needs every remote pose in a shared frame plus `frameReady` — it belongs to the removed architecture.
- **Authority re-checks it.** `BodyObservation` on the wire is `{targetPlayerId, capturedAtMs, associationConfidence, uncertaintyMeters, colliders}` ([combat-protocol/src/index.ts](../../packages/combat-protocol/src/index.ts)). In `packages/combat-simulation/src/index.ts` the fire handler in sighting mode rejects with `ambiguousTarget` whenever `opponents.length !== 1`, rejects `invalidInput` unless `observation.targetPlayerId` is that single opponent, and rejects `noSighting` when the observation is older than `COVER_OBSERVATION_MS = 1000`, `associationConfidence < 0.8`, `uncertaintyMeters > 0.1`, or has no colliders. So 3–4 players is blocked on **both** client and authority today; any identity signal needs a simulation-rule change as well as a client change (not in scope here — noted as a dependency).
- **Skeleton source.** `TargetingSession.swift` runs `ARBodyTrackingConfiguration` when `ARBodyTrackingConfiguration.isSupported` (3D `ARBodyAnchor` skeleton in the local ARKit frame) and otherwise `ARWorldTrackingConfiguration` + Vision `VNDetectHumanBodyPoseRequest` (2D joints). Both configurations use `worldAlignment = .gravity`. This matters for §4.3 (camera assistance requires a *world-tracking* configuration).
- **Roster.** Convex lobby knows members `{playerId, displayName, role}` and enforces `GAMEPLAY.maxPlayers = 2` (`convex/domain/config.ts`); `AGENTS.md` sets the Phase 1 cap at 4. The Worker relays an opaque `niToken` per player (`niTokenBytes: 4096`, `room.ts` `niTokens` map, replayed on join, cleared on reset). **Absence:** no code path relays NI ranging *samples* between phones or to the Worker; only tokens.
- **Existing NI stack** ([NearbySessionManager.swift](../../ios/VictoriaKillZone/VictoriaKillZone/Targeting/NearbyInteraction/NearbySessionManager.swift), [NearbyRendezvousPolicy.swift](../../ios/VictoriaKillZone/VictoriaKillZone/Targeting/NearbyInteraction/NearbyRendezvousPolicy.swift), [NearbyRendezvous.swift](../../ios/VictoriaKillZone/VictoriaKillZone/Features/Realtime/NearbyRendezvous.swift)): one `NISession` per peer, `NearbyRendezvousPolicy.maximumPeers = 3`, capability probe via `NISession.deviceCapabilities`, ordered hedge `.plain → .cameraAssisted → .distanceOnly`, 200 ms pump, 40-sample window, ≤ 6 s sample age, re-run on suspension/timeout, and a *graph solve of a host frame transform* consumed by the collaborative path (`usesNearbyRendezvous` is true only when `usesCollaborativeFrame`). `Info.plist` already carries `NSNearbyInteractionUsageDescription` ("…so the arena lines up without scanning the room"), `NSLocalNetworkUsageDescription`, `NSBonjourServices`, and `NSCameraUsageDescription`. `docs/build-log.md` records **no physical NI/UWB evidence** for any slice.

## 3. What Apple documents about Nearby Interaction (confirmed, primary)

### 3.1 Capability, devices, regions

- NI runs only on devices with a UWB chip; feature support is queried at runtime from `NISession.deviceCapabilities`: `supportsPreciseDistanceMeasurement`, `supportsDirectionMeasurement`, `supportsCameraAssistance`, `supportsExtendedDistanceMeasurement`, plus newer `supportsDLTDOAMeasurement` and `supportsBluetoothChannelSounding` [1][2].
- Device matrix (Apple Support, published 2026-03-27) [3]: **first-generation UWB** — iPhone 11, 12, 13, 14 (all models); **second-generation UWB** — iPhone 15 models and later **excluding iPhone 16e and iPhone 17e**, plus iPhone Air. Every iPhone older than 11, the SE line, 16e and 17e have **no UWB**. UWB is disabled entirely in Armenia, Azerbaijan, Belarus, Kazakhstan, Kyrgyzstan, Russia, Tajikistan, Turkmenistan, Ukraine and Uzbekistan; in Japan some frequencies are unavailable and devices fall back to previous-generation behaviour; in Indonesia and Nepal only iPhone 17 / iPhone Air (and some accessories) may use it. **(inference)** Therefore the fleet in Victoria, BC is nominally UWB-capable on any 2019-or-later non-e/non-SE iPhone, but the app must treat UWB as *optional per phone*, never as a match requirement.
- **Absence:** Apple publishes no per-model table of *direction* support. The API contract is only "check `supportsDirectionMeasurement` at runtime" [1]. Predecessor claims that all U1/U2 iPhones report direction are inference, not documentation.
- Extended Distance Measurement (EDM) requires second-generation UWB on **both** phones and iOS 17 [4]; Apple's sample uses 10 m / 50 m working constants in its distance-quality estimator [4]. `activeExtendedDistanceSessionsLimitExceeded` exists as a distinct error [5].

### 3.2 Session model and limits

- One `NISession` per peer; sessions are bi-directional; "Each device can run several sessions at the same time, each session with one other peer" — Apple's WWDC20 graphic shows **four devices each running three sessions in parallel** [6]. That is exactly the 4-player topology (and matches `NearbyRendezvousPolicy.maximumPeers = 3`).
- **Absence:** Apple publishes **no numeric cap** on concurrent sessions; the only surface is `NIError.Code.activeSessionsLimitExceeded` ("the app reached the maximum number of sessions") [5]. The WWDC20 three-sessions-per-device illustration is the strongest primary evidence that three simultaneous peers is an intended configuration, but it is a slide, not a guarantee.
- Peers are discovered and `discoveryToken`s exchanged over any transport the app chooses (Core Bluetooth, Multipeer Connectivity, "or a custom server deployment") [1]. The repository already uses the custom-server route (Worker `niToken` relay) — Multipeer Connectivity is **not required**. If MPC were used, `MCSession` supports up to 8 peers including local [7] and needs `NSBonjourServices` + `NSLocalNetworkUsageDescription` [8] (both already present).
- **Permission:** first run prompts with `NSNearbyInteractionUsageDescription`; the user's choice persists in Settings [1]. WWDC20 described the grant as one-time "until your app is exited" [6]; the current documentation says the system persists the choice and consults it before new sessions [1]. **(inference)** Treat the permission as a runtime capability that can be absent on any peer; the prompt is user-visible and must not block match start.
- **Background:** backgrounding suspends every session (`sessionWasSuspended`); a suspended session never resumes on its own — the app must call `run(_:)` again after `sessionSuspensionEnded`; stay backgrounded too long and the session is invalidated and the peer sees `didRemove … .timeout` [9]. There is no background NI between iPhones (background NI is documented only for Bluetooth-paired UWB *accessories*) [10]. For a foreground game this is acceptable; the existing manager already re-runs on suspension.
- `resourceUsageTimeout` invalidates a session the framework has timed out [5]; the existing code treats that as re-run.

### 3.3 Measurement geometry

- `NINearbyObject.distance` is metres; `direction` is "a three-dimensional unit vector pointing at the other device, **relative to the local device itself**" [6][11]. Both are optional: out of range → both `nil`; out of the direction cone → `direction` `nil`, distance may continue [1][6].
- Best operation: peers **within 9 m**, in **portrait**, **back cameras facing each other**, clear line of sight; the direction cone "roughly corresponds with the Ultra Wide camera's field of view on the iPhone 11"; one phone in landscape sharply reduces availability; people, walls and vehicles between phones reduce availability [1][6].
- **Camera Assistance** (iOS 16+, `isCameraAssistanceEnabled`) fuses ARKit 6-DoF tracking with UWB, "increases the device's line of sight to a larger area", adds `horizontalAngle` and `verticalDirectionEstimate`, and exposes `NISession.worldTransform(for:)` (peer transform in the local ARKit world) and a convergence coaching API [12][13][14]. Apple's guidance: this capability "is best used for interacting with **stationary** devices" [10]; the Precision-Finding sample rests one phone on a table [4].
- Camera Assistance and ARKit share one process: "Only a single ARSession can be running for a given application", so an app with its own AR experience **must** hand its session to NI via `setARSession(_:)` **before** `run` [10][15]. The shared session must be an **`ARWorldTrackingConfiguration`** with `worldAlignment = .gravity`, `isCollaborationEnabled = false`, `userFaceTrackingEnabled = false`, `initialWorldMap = nil`, and a delegate returning `false` from `sessionShouldAttemptRelocalization` — otherwise NI invalidates with `invalidARConfiguration` [15][10]. Removing collaboration and world-map loading *satisfies* three of these conditions; see §4.3 for the one it does not.

### 3.4 Accuracy and rate — what is and is not documented

- **Absence:** Apple publishes no numeric accuracy or update-rate figure for iPhone-to-iPhone NI. The only Apple-sourced numbers are the 9 m best-operation envelope [1] and the EDM sample's 10 m / 50 m constants [4].
- **[academic]** Nearby Interaction distance updates observed at ≈ 5 Hz (SmartPoser) [16]. **[academic]** consumer-smartphone UWB average ranging error < 20 cm in controlled settings (summary in Jutterström 2026) [17]. **[practitioner]** phone-to-accessory ranging 5–10 m indoors, 30–40 m in the open with degradation through bodies [18]. None of these were collected on our devices or in our outdoor scenario; none measure *direction* accuracy between two *moving, hand-held* phones, which is what identity fusion needs. That gap is the central unknown (§6).

## 4. Fusing per-peer radio bearing/distance with the camera ray — no shared frame required

### 4.1 Why this is a different problem from the removed rendezvous

`NearbyRendezvousCoordinator` used NI to *solve a transform between phones' AR frames* (host graph alignment, 40-sample windows, pointing/retry phases, gating collaboration) so that remote self-reported poses could be projected into the local camera. Identity fusion needs none of that. Every quantity below lives in the **shooter's own frame**:

| Quantity | Frame | Source |
|---|---|---|
| Ray to the sighted body (camera → root/torso joint) | shooter's ARKit world (or camera image plane on 2D Vision path) | `ARBodyAnchor` / Vision joints (existing) |
| Direction to peer *k* | shooter's device coordinates → rotate by the current camera transform into shooter's ARKit world | `NINearbyObject.direction` (plain NI) |
| Distance to peer *k* | scalar | `NINearbyObject.distance` |

No token from peer *k* is ever interpreted geometrically by the shooter beyond "this session ranges to player *k*". The mapping token→playerId already exists (Worker `niToken` relay keyed by `playerId`). No calibration ritual, no host frame, no `frameReady`, no collaboration data. **(inference)** This is the only property that makes NI compatible with "start is never gated": if a peer's radio is silent, the fusion simply has fewer candidates.

### 4.2 Association rule (proposal; thresholds unmeasured)

For a fire command at time *t*, with skeleton `S` and per-peer latest samples `(d_k, u_k, age_k)`:

1. Candidate set `C` = connected opponents with a sample fresh enough (age ≤ *A*, order 0.5 s given ≈ 5 Hz updates [16] and a 100 ms skeleton freshness window).
2. Angular residual `θ_k = angle(ray_S, R_cam · u_k)` for peers whose `u_k` is non-nil; distance residual `δ_k = |‖p_S − p_cam‖ − d_k|` where the body's 3D position exists (`ARBodyAnchor` path) — on the Vision-only path, `δ_k` is unavailable and only `θ_k` (projected to the image) applies.
3. Winner = argmin of a combined score; **accept only if** the runner-up exceeds the winner by a margin (angular margin *M_θ*, distance margin *M_d*) — the same "nearest with margin" shape as the existing `associate(...)` (0.35 m margin), re-expressed in radio units.
4. If exactly one opponent has any radio sample and its residuals pass, accept it. If no radio samples exist (non-UWB shooter or peers) fall to §5.
5. Emit `BodyObservation.associationConfidence` from the margin (so the authority's existing ≥ 0.8 gate stays meaningful) and keep `uncertaintyMeters` bound to the skeleton, not the radio.

**Why direction, not distance, carries the identity.** Two opponents standing 5 m and 5.4 m away are indistinguishable by distance given ≈ 20 cm-class UWB error **[academic]** [17] plus body-depth error, but are separated by several degrees of bearing at any realistic lateral spacing (**(inference)** two bodies 1 m apart at 6 m subtend ≈ 9.5°). Distance-only (U1 phone outside the direction cone, or peer in landscape) is a *weak* tiebreaker; it can still decide when opponents are at clearly different ranges (e.g. 3 m vs 9 m).

**Direction is only available inside a rear-facing cone roughly the Ultra Wide camera's FoV [6].** The camera ray to a *sighted* body is by construction inside the main camera's FoV, which is narrower than Ultra Wide, so **(inference)** when the shooter aims at an opponent, that opponent's phone is normally inside the UWB direction cone *if the opponent holds the phone in front of their body in portrait* — the ADR 0013 play posture. Opponents outside the shooter's FoV are the ones expected to lose direction, and they are exactly the ones the sighting cannot be, so `direction == nil` for a non-sighted peer is not harmful. The failure case is a sighted opponent whose phone is pocketed, lowered or in landscape: direction drops to `nil` and the rule degrades to distance-only or to §5.

### 4.3 Plain NI vs Camera Assistance for this use

- **Plain NI is the primary path.** It needs no ARSession, so it coexists with the targeting session's `ARBodyTrackingConfiguration` unchanged. Its `direction` is in device coordinates [6][11]; rotating into the ARKit world uses the current `ARFrame.camera.transform` the targeting code already holds. **(inference)** Direction updates at ≈ 5 Hz [16] against a 100 ms skeleton window means the fused sample may be up to ~200 ms stale; a shooter panning at 60°/s therefore carries ≈ 12° of bearing lag — the margin *M_θ* must absorb this or the rule must extrapolate using the camera's own rotation (which is known at 60 Hz).
- **Camera Assistance is blocked by an ARKit configuration conflict, not by the shared-frame removal.** `setARSession` requires an `ARWorldTrackingConfiguration` [15]; the targeting session runs `ARBodyTrackingConfiguration` on every phone that supports it (§2). Running a second ARSession is disallowed [10]. **Absence:** Apple does not document whether NI accepts an `ARBodyTrackingConfiguration`-driven session; the documented outcome for a non-conforming configuration is `invalidARConfiguration` [15]. Camera Assistance is also documented as best for **stationary** peers [10], while Quick Duel opponents move. Both facts argue against depending on it. It remains an opt-in experiment on the Vision-only path (which does run `ARWorldTrackingConfiguration`), where `worldTransform(for:)` would place the peer directly in the shooter's frame — but that path also lacks a 3D body position, so the gain is limited to bearing robustness. Removing collaboration/`initialWorldMap` **does** remove two of the previous blockers, so the existing hedge order `.plain → .cameraAssisted → .distanceOnly` is *reversed* in value for identity: plain first, distance-only second, camera-assisted last and only where the AR configuration permits.

### 4.4 Power/thermal

**Absence:** Apple publishes no NI power figures. The predecessor listed "battery/thermal cost of camera+UWB+P2P concurrently" as an unmeasured device question [shared-arena-frame-options §6.4]; this brief adds nothing measured. **(inference)** Three concurrent NI sessions plus ARKit body tracking plus Vision plus the Worker WebSocket is the maximum load the app has ever attempted; `ProcessInfo.thermalState` logging must be in the first device run (§6). Adaptive behaviour (drop to 1–2 sessions, or pause NI when only one opponent is connected) is a design option, not a measured need.

## 5. Bluetooth RSSI, and the graceful fallback on non-UWB phones

- **Core Bluetooth RSSI** is available at discovery (`centralManager(_:didDiscover:advertisementData:rssi:)`) and on a connected peripheral (`readRSSI()` → `peripheral(_:didReadRSSI:error:)`) [19][20]. Apple documents it as a signal-strength indicator only; **absence:** no Apple documentation offers distance or bearing from RSSI, and iPhone-to-iPhone Core Bluetooth requires one side to act as `CBPeripheralManager` advertiser. Foreground-only apps cannot scan or advertise in the background [21] — same envelope as NI, so no advantage there. **(inference)** RSSI varies by tens of dB with hand grip, body shadowing and orientation, so it can at best order two opponents when they are at *grossly* different ranges (e.g. 2 m vs 12 m); it carries no bearing and cannot separate two opponents in the same general direction. It is not an identity signal; it is at most a low-weight tiebreaker with a permission cost (`NSBluetoothAlwaysUsageDescription`, not present today) and a discovery cost. **Recommendation: do not build it.**
- **Non-UWB phones (iPhone SE, 16e, 17e, ≤ iPhone XS, UWB-disabled regions, permission denied).** Identity must come from the camera plus the authority's own state. Candidate behaviours that stay inside the zero-setup rule, all **(inference)**, none device-tested:
  1. **Unique-candidate rule generalised by connectivity and posture**: when only one opponent is `connected`, or only one opponent's self-reported pose stream (`PlayerPhonePose` — a pose in that player's *own* frame, so only its speed/stillness is frame-independent) is consistent with the sighted body's observed motion (walking vs still), accept it — cheap, weak.
  2. **Authority-side plausibility instead of client identity**: the client sends the sighting with `targetPlayerId = null` and the colliders; the DO scores the shot against *every* opponent's recent self-reported phone pose stream **in the shooter's frame** — but that needs a shooter→target transform, i.e. the removed shared frame. **Not viable** without alignment; listed to close it explicitly.
  3. **Team/visual differentiation** (armband colour, jersey number detected in the crop): a vision classifier on the detected body crop keyed to a colour chosen in the lobby. Zero radio dependence, works for 4 players, respects "no visible target markers" only if the colour is clothing the player already wears (a design/ADR question; markers are prohibited by `AGENTS.md`). Recorded as an option requiring a decision record, not recommended here.
  4. **Ambiguity is a legal outcome**: keep `ambiguousTarget`/`noSighting` semantics — the shot flies with no body observation (projectile physics only, as today when association fails). For 3–4 players on a non-UWB phone this means body hits only register when identity is unambiguous (one opponent connected, or radio-identified on the shooter's side). This is the *graceful* floor: it never blocks start, never blocks firing, and degrades hit registration rather than the match.
- The fallback the brief recommends is **4 with 1 as a cheap enhancement**: radio identity where both phones have UWB and permission; unique-candidate where they do not; the shot always fires. Mixed rosters therefore have asymmetric hit registration (a UWB shooter can hit any of three opponents; a non-UWB shooter can register body hits only when one candidate remains). That asymmetry is a product decision to surface, not hide (§7).

## 6. What cannot be known without device experiments

1. Direction availability and angular error between two **moving, hand-held** iPhones in portrait at 3–9 m outdoors, per generation pair (U1–U1, U1–U2, U2–U2). Apple's 9 m / portrait / facing envelope is documented; its *error* is not.
2. Whether three simultaneous `NISession`s per phone actually run on our devices without `activeSessionsLimitExceeded` or `resourceUsageTimeout`, and at what per-session update rate (single-peer ≈ 5 Hz is a third-party observation).
3. Whether `direction` remains available when the *opponent* aims back (both phones in portrait facing each other is Apple's best case) versus when the opponent's phone is lowered.
4. Whether NI with `isCameraAssistanceEnabled` accepts an `ARBodyTrackingConfiguration` session or invalidates with `invalidARConfiguration` (expected: invalidates; undocumented).
5. Thermal state and battery drain over a 3-minute match with 3 sessions + body tracking + Vision.
6. Achievable angular margin *M_θ* and false-identity rate when two opponents stand ≤ 1 m apart at 6 m.

Minimum protocol: three or four named iPhones (record model, iOS build, UWB generation), 3 m / 6 m / 9 m cone markers, logged CSV per phone of `distance`, `direction`, `age`, camera transform, detected-body ray, `thermalState`; static then walking; recorded in `docs/build-log.md` with device names before any ADR.

## 7. Recommendation

- **Viable as an identity signal for 3–4 players — conditionally, and only as an optional per-shooter enhancement.** The primary evidence is Apple's own: direction is a device-relative unit vector [6][11], several sessions per device with four devices × three sessions is Apple's illustrated topology [6], and no shared frame is required for the fusion in §4.2. The conditions are (a) plain NI, not Camera Assistance (§4.3); (b) both shooter and target have UWB and granted permission; (c) an angular-margin rule with thresholds set from device data (§6), not from this brief.
- **Never a start gate, never a match requirement.** UWB is optional per phone (SE/16e/17e/regional/permission). Absence of radio identity degrades to the §5 floor (shots fire; body hits register only when the candidate is unique). Surface the asymmetry in the lobby ("precision ID available/unavailable") rather than blocking anyone.
- **Do not reuse `NearbyRendezvousCoordinator` semantics.** Keep only the reusable primitives from `NearbySessionManager`: per-peer session lifecycle, capability probe, token relay via the Worker, suspension re-run. Drop the phases, the graph solve, the 40-sample window, host alignment, and the `.cameraAssisted` hedge. The usage description must be rewritten for the new purpose (current copy promises arena alignment) — a `Info.plist` change owned by Integration.
- **Bluetooth RSSI: reject.** No bearing, permission cost, coarse-range-only value.
- **Prerequisite changes outside this brief** (for the record, no implementation here): simulation rule replacing `opponents.length !== 1 → ambiguousTarget` with "targetPlayerId ∈ opponents"; Convex `maxPlayers` 2 → ≤ 4; `RealtimeAssociationPolicy.associateSighting` accepting a candidate ranking; a sample-fusion type carrying `(playerId, distance, direction, sampledAt)` on the client only — samples never need to cross the network.
- **Decision gate:** run the §6 protocol before an ADR. If direction is unavailable or noisier than the required margin on moving phones, the honest outcome is that Quick Duel with 3–4 players ships with the §5 floor only, and radio identity waits for hardware with wider-cone direction (documented for no shipped iPhone as of the cited support page).
